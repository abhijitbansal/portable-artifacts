# make-demo phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the skill an approved click plan and get a take folder: the approved rows run once, frame by frame, with every
frame a 3x picture, masked where it must be, plus a contact sheet and a report of what the site did.

**Architecture:** `take.mjs` checks the answers through make-explainer's `answers.mjs` and the recomputed plan hash, then runs
the plan's rows in one guarded browser context under phase 0's stepped clock. Before each act it re-reads the live control and
compares it with what was approved. Any row that cannot run stops the take and keeps what it has. Frames go to phase 0's frame
store. No model call happens during a take.

**Tech Stack:** Node 20+, Playwright 1.64.0, ajv 8.20.0 (already pinned). No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-24-make-demo-design.md` sections 6.4 to 6.6; hand-off
`docs/superpowers/plans/2026-11-26-make-demo-handoff-p2.md`; phase 1 plan `docs/superpowers/plans/2026-11-24-make-demo-p1.md`.

## The claim of this phase

1. A take runs only the rows of the plan the owner approved: the recomputed hash equals the plan page's key and the answers'
   `planKey`, the verdict is `approve`, and each `danger` row has its own answered `approve` (`rows-as-listed` when there is
   none). Nothing else is clicked, typed, pressed or opened.
2. Before each act the live control is the approved one (role, name, kind, address, form). Otherwise the take stops there.
3. A new origin, an intent row, a `look` row followed by a new same-site write, a stuck page or a limit stops the take, and
   the report says which row and why.
4. On a signed-in take no password, email, long number or key, and no `mask` target, is in any frame, the contact sheet,
   `take.json` or a printed line. `mask` targets are hidden signed out too.

A finding outside this claim that is not an obvious failure goes to "Known limits".

## Owner's answers (2026-11-26)

- **No pause.** A row that cannot run stops the take and keeps the frames so far. Pause and resume are a later phase, if wanted.
- **Downloads are kept** in the take folder, capped, never opened by the model, listed in the report.
- **The site's own writes** all run and are listed. A take stops only when a `look` row is followed by a non-GET request to an
  origin in `origins` that scout did not list for that page. Third-party posts are listed, never a stop.
- **Real time is deferred.** Phase 2 is frame by frame only. A plan whose `scout.json` says `stepped.ok: false` is refused
  before the browser starts: "this page cannot be filmed frame by frame; real-time capture is not built yet".

## Review Focus

1. A same-named control appears on the live page that scout did not see (two "Save" buttons): the take stops, it does not pick
   one (Task 1).
2. A change click that submits a form whose `action` moved to another origin since scout: the navigation is refused and the
   take stops at that row (Task 1).
3. An answers file with verdict `approve-with-changes`, or a `danger-<id>` row left unanswered: refused before a browser starts
   (Task 2).
4. A signed-in page that renders an email after a delay (a fetch that lands during settle): no frame holds it (Task 3).
5. A download with a hostile suggested name (`../../x`, a newline, 300 characters): stored under a name of our own, the
   suggested name shown only through `agentText` (Task 4).

**Interfaces:**

## How it is built

Six builder dispatches at most, one per task 1 to 6, in order, Sonnet at high effort: each needs the interface before it, and
the browser is a serial resource. The main session reviews each diff, runs the suites, commits and pushes. Then one reviewer.
No other agents.

## Known limits, to be stated

- Frame by frame only. A page with a playing video, or one that does not settle, cannot be taken yet.
- No pause: an unknown screen, a changed control or a sneaky write ends the take. Retaking repeats every `change` row.
- The first write of a sneaky `look` row has gone before the take stops.
- Masking covers emails, long numbers, keys, password fields and `mask` targets. Names, faces, short codes, amounts, text in a
  canvas, in a cross-origin frame or in a picture are not masked.
- Settled frames are as the stepped clock shows them; a page that reads real time in a worker is not stepped.
- Downloads are kept as the site sent them; their content is never checked.
- Signed in, names are masked, so a twin control with the same masked name is not detected; the css, role and kind must
  still match.
- The hash shows drift. It does not stop an agent that forges an answers file.
